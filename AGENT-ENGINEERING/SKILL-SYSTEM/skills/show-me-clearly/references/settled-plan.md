# Subject: settled phased plan

Read this before writing an explanation of an already-settled phased plan. It
assumes the spine, prose rules, and visual limits in `SKILL.md`.

## Do not design the plan

Preserve the supplied phase boundaries. If the phases are not settled, stop and
ask rather than designing them inside this skill. Label planned work `proposed`
and do not imply a head revision exists.

## Start with a small phase roadmap

The orientation element is a phase roadmap: one line per phase, inside the
usual visual limits. Order it the way the work lands, not the way the plan
document happens to be organized.

## Answer four questions per phase

For each phase, answer:

1. What becomes true when this phase is done?
2. Why does this phase come now — what does it depend on?
3. Where does the work live in the repository?
4. How will completion be observed?

Question 3 anchors the phase in real paths, which is what keeps the document
from becoming a paraphrase of the plan. Cite baseline code for what exists
today; label everything else `proposed`.
